# Technical Docs QA — 产品经理视角

---

## 一、目标用户与核心痛点

| 用户类型 | 核心需求 | 当前痛点 |
|---|---|---|
| 技术支持团队 | 快速找到产品手册/API文档中的答案 | 文档繁多，人工检索耗时，新人上手慢 |
| 开发者/工程师 | 查询内部技术规范、接口文档 | 文档分散在 Confluence/Wiki，搜索不精准 |
| 售前/解决方案工程师 | 快速回答客户的技术问题 | 依赖资深工程师，响应不及时 |
| 新员工 | 快速了解产品技术细节 | 培训周期长，找人问耗费他人时间 |

**核心价值主张**：把散落在文档库里的技术知识，变成可以随时对话查询的智能助手——"问就有答案，答案有来源"。

---

## 二、功能设计的 PM 逻辑

### 2.1 单 Agent + 内置 Retrieval — 最小可用设计

这是 RAGFlow 所有问答模板中**节点最少的一个**，体现了"够用就好"的设计哲学：
- 不做多轮追问的对话管理
- 不做意图分类
- 不做多知识库路由
- 专注于：用户问 → 检索文档 → 给答案

**PM 洞察**：这个模板的价值在于它是**其他复杂知识库模板的基础组件**。理解它，才能理解 `choose_your_knowledge_base_agent`、`knowledge_base_report` 等更复杂的变体是如何在此基础上扩展的。

### 2.2 面向技术文档的定位

模板名称明确写了"Technical Docs"，说明它的设计预设：
- 文档是结构化的技术内容（API 文档、操作手册、架构设计文档）
- 用户的提问是精确的技术查询，而非模糊的业务问题
- 答案需要**精确引用文档原文**，而非 AI 自由发挥

## 三、产品边界

### 适用场景
- 技术产品的内部知识库问答
- API 文档 / SDK 文档查询助手
- 内部技术规范和操作手册查询
- 开发者门户的智能搜索

### 不适用场景

| 场景 | 原因 | 替代方案 |
|---|---|---|
| **跨多个知识库查询** | 单一知识库绑定 | `choose_your_knowledge_base_agent` |
| **需要联网获取最新信息** | 仅检索已有文档 | `web_search_assistant` |
| **需要生成报告/总结** | 只做问答，不做综合报告 | `knowledge_base_report` |
| **业务/客服类问题** | 定位技术文档，不适合非技术场景 | `customer_service` / `customer_support` |

## 四、产品成熟度评估

| 评估维度 | 评分 | 说明 |
|---|---|---|
| **需求清晰度** | ★★★★★ | 技术文档问答场景极其明确 |
| **架构简洁性** | ★★★★★ | 最简 RAG 架构，易于理解和维护 |
| **开箱即用性** | ★★★☆☆ | 需要先建好知识库并上传文档 |
| **回答质量** | ★★★★☆ | 依赖知识库质量，文档质量好则回答好 |
| **可扩展性** | ★★★★★ | 是所有复杂知识库模板的基础，扩展路径清晰 |

---

## 五、迭代方向建议

1. **多知识库路由**：增加 Categorize 节点，根据问题类型检索不同知识库（API文档库/架构文档库/FAQ库）
2. **引用溯源显示**：在回答后自动附上引用的文档章节和页码
3. **置信度提示**：检索相似度低时主动提示"未找到相关文档，以下为 AI 推断"
4. **多轮对话追问**：支持基于上文继续追问，无需每次重新描述背景
