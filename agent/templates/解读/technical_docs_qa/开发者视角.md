# Technical Docs QA — 开发者视角

---

## 一、节点类型全景

| 节点类型 | 实例 | 作用 |
|---|---|---|
| `Begin` | begin | 对话入口，接收用户问题 |
| `Agent` | 核心 Agent | 调用内置 Retrieval 工具检索知识库，生成回答 |
| `Message` | 输出节点 | 展示回答给用户 |

这是 RAGFlow 所有对话模板中**节点数最少的架构**，三个节点完成完整的 RAG 问答流程。

---

## 二、数据流分析

```
begin
  └── sys.query（用户问题）
          │
          ↓
Agent（内置 Retrieval 工具）
  1. 接收 sys.query
  2. 调用 Retrieval 工具：
     → 向量检索知识库，获取 Top-K 相关文档片段
     → 将检索结果注入 Agent 上下文
  3. LLM 基于检索内容生成回答
  4. 输出 @content
          │
          ↓
Message
  内容：{Agent@content}
          │
          ↓
用户界面
```

**关键机制**：Retrieval 是 Agent 的**内置工具**（不是独立节点），Agent 自主决定何时调用、调用多少次。这与 `choose_your_knowledge_base_workflow` 不同——后者 Retrieval 是独立节点，由图执行引擎强制调用。

---

## 三、两种 RAG 架构的对比

理解这个模板，关键在于理解 RAGFlow 的两种 RAG 实现方式：

| 方式 | 代表模板 | Retrieval 位置 | 控制权 |
|---|---|---|---|
| **Agent 内置 Retrieval** | `technical_docs_qa` | Agent 的工具列表中 | Agent 自主决定调用时机和次数 |
| **独立 Retrieval 节点** | `choose_your_knowledge_base_workflow` | 图中独立节点 | 执行引擎强制在 Agent 前调用 |

**工程含义**：
- 内置方式：更灵活，Agent 可以多次检索、调整查询词，适合复杂问题
- 独立节点方式：更可控，检索结果固定，适合需要精确控制的场景

---

## 四、关键配置点

### 知识库绑定
Agent 的 Retrieval 工具需要绑定具体的知识库 ID。模板中此处为空，**需要部署时手动选择知识库**。

### Retrieval 参数（通常可配置）
- **Top-K**：返回多少个文档片段（影响上下文长度和回答质量）
- **相似度阈值**：低于此分数的片段不返回（影响回答的精准度）
- **检索模式**：向量检索 / 全文检索 / 混合检索

### 模型选择
使用标准对话模型即可，不需要长上下文模型（因为文档片段已经由 Retrieval 做了筛选压缩）。

---

## 五、已知局限

| 局限 | 影响 | 改造方向 |
|---|---|---|
| 单一知识库 | 无法跨库检索 | 增加 Categorize 节点路由到不同知识库 |
| 无引用溯源 | 用户不知道答案来自哪个文档 | 在 system prompt 中要求输出引用来源 |
| 无置信度控制 | 知识库中没有相关内容时 LLM 可能"编造" | 设置相似度阈值，低于阈值时输出"未找到相关文档" |

---

## 六、落地配置

```
1. 在 RAGFlow 创建知识库，上传技术文档（PDF/Word/Markdown）
2. 等待文档解析和向量化完成
3. 导入模板，在 Agent 节点的 Retrieval 工具中选择对应知识库
4. 配置模型（任意支持的 LLM 均可）
5. 测试：提几个文档中有明确答案的问题，验证检索准确性
```
