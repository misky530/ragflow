# SQL Assistant — 产品经理视角

---

## 一、目标用户与核心痛点

| 用户类型 | 核心需求 | 当前痛点 |
|---|---|---|
| 业务分析师 | 快速查询数据库，不想写 SQL | 依赖 BI 工具或请求数据团队，响应慢 |
| 产品经理 | 自助查询产品数据 | 没有 SQL 能力，需要排队等数据工程师 |
| 运营人员 | 实时查询运营指标 | BI 报表不够灵活，自定义查询门槛高 |
| 销售/BD | 查询客户数据、合同信息 | CRM 查询功能有限，复杂筛选需要 IT 支持 |

**核心价值主张**：让不会写 SQL 的业务人员，用自然语言直接查询数据库——把"请 IT 帮忙取数"变成"自己问 AI 取数"。

---

## 二、功能设计的 PM 逻辑

### 2.1 并行 Retrieval — 为什么要检索三个知识库？

三个 Retrieval 节点并行工作，各自检索不同的知识库：
1. **表结构库**：数据库的表名、字段名、字段类型
2. **字段说明库**：业务语义（`user_type=1` 表示企业用户）
3. **查询示例库**：历史 SQL 查询样例（few-shot 学习）

**PM 洞察**：这是 Text-to-SQL 准确率的关键——LLM 需要知道"这个数据库有哪些表、每个字段的业务含义、过去类似的问题是怎么查的"，才能写出正确的 SQL。三个维度缺一不可。

### 2.2 ExeSQL — 从"生成 SQL"到"执行并返回数据"

这个模板不只是生成 SQL 文本，还通过 `ExeSQL` 节点**真正执行 SQL** 并返回结果。

**PM 洞察**：这是与纯文本 AI 工具的核心区别。大多数 AI 工具只能生成 SQL 代码，用户还需要自己去数据库里运行。`ExeSQL` 直接打通了"生成→执行→返回数据"的完整链路，真正实现了自助取数。

## 三、产品边界

### 适用场景
- 内部数据自助查询（销售数据、用户数据、运营指标）
- 报表灵活自定义（标准报表覆盖不到的临时查询）
- 数据探索（业务人员自主发现数据中的规律）

### 不适用场景

| 场景 | 原因 | 风险 |
|---|---|---|
| **写入/修改操作** | ExeSQL 应限制为只读查询，但需要配置层保证 | 误删数据风险 |
| **超复杂 SQL**（多层嵌套、窗口函数） | Text-to-SQL 准确率随复杂度下降 | 生成错误 SQL，返回错误数据 |
| **敏感数据库**（含个人隐私、金融数据） | 自然语言查询难以做细粒度权限控制 | 数据泄露风险 |
| **实时流数据** | 依赖 RAG 检索 Schema，不适合动态变化的 Schema | 结果滞后 |

## 四、产品成熟度评估

| 评估维度 | 评分 | 说明 |
|---|---|---|
| **需求真实性** | ★★★★★ | 自助取数是企业数字化的普遍痛点 |
| **技术复杂度** | ★★★★★ | 引入 ExeSQL，是模板库中最复杂的执行链路 |
| **安全风险** | ★★☆☆☆ | 需要严格的数据库权限控制，否则风险极高 |
| **开箱即用性** | ★★☆☆☆ | 需要建好三个 Schema 知识库，配置数据库连接 |
| **SQL 准确率** | ★★★☆☆ | 依赖 Schema 知识库质量，简单查询准确，复杂查询不稳定 |

---

## 五、迭代方向建议

1. **只读权限强制**：ExeSQL 节点配置只允许 SELECT 语句，拒绝 INSERT/UPDATE/DELETE
2. **SQL 审核节点**：在 ExeSQL 前增加 SQL 审核 Agent，检查 SQL 的安全性和逻辑正确性
3. **结果可视化**：查询结果接入图表生成节点，自动生成柱状图/折线图
4. **查询历史记录**：保存历史查询，支持相似查询复用
