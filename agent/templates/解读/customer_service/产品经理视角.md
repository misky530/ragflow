# Customer Service — 产品经理视角

---

## 一、目标用户与核心痛点

| 用户类型 | 核心需求 | 当前痛点 |
|---|---|---|
| 客服主管 | 不同类型问题由不同专业团队处理 | 一线客服需要判断分类再转接，效率低 |
| 电商/零售企业 | 售前咨询和售后投诉需要不同话术和知识库 | 同一客服系统服务所有类型，专业性差 |
| SaaS 公司 | 技术问题和账单问题需要不同专业知识 | 客服人员全能要求高，培训成本大 |

**核心价值主张**：一个入口，多种专业——用户不需要知道该找哪个部门，系统自动识别并用最专业的方式回答。

---

## 二、功能设计的 PM 逻辑

### 2.1 四类意图设计

```
售前咨询（Pre-sales）
  → 产品功能介绍、价格咨询、方案对比
  → 使用产品知识库 + 销售话术

售后支持（After-sales support）
  → 使用问题、操作引导、功能疑问
  → 使用操作手册知识库

投诉处理（Complaint）
  → 退款、损坏、服务不满意
  → 使用退款政策知识库 + 安抚话术

其他（General）
  → 不符合以上任何类别的问题
  → 通用回答
```

**PM 洞察**：四类是最小完备集——覆盖了客服场景的核心意图，又不至于过度细分（细分过多会增加误分类概率）。

### 2.2 VariableAggregator — 多路汇合的产品意义

四个分支的输出需要汇合到一个变量，才能传给统一的 Message 节点输出。

**PM 洞察**：这是多分支工作流的**必备模式**。没有 VariableAggregator，系统就不知道最终该输出哪个分支的内容。它解决了"分支结果汇总"这个工程问题，让多分支架构成为可能。

## 三、与 customer_support 的差异

这两个模板功能高度相似，差异在：

| 维度 | customer_service | customer_support |
|---|---|---|
| 节点汇合方式 | VariableAggregator | 无（或直接 Message） |
| canvas_type | 可能不同 | 可能不同 |
| 分支数量 | 4类 | 可能略有不同 |

---

## 四、产品成熟度评估

| 评估维度 | 评分 | 说明 |
|---|---|---|
| **意图分类设计** | ★★★★☆ | 四类覆盖基本场景，实际业务可能需要扩展 |
| **分支专业化** | ★★★★☆ | 各分支可配置独立知识库，专业性强 |
| **开箱即用性** | ★★★☆☆ | 需要为各分支准备对应知识库 |
| **可扩展性** | ★★★★★ | 新增意图类别成本低，新加 Categorize 选项 + Agent 节点即可 |

---

## 五、迭代方向建议

1. **意图扩展**：根据实际业务数据，识别高频未覆盖意图，新增分支
2. **置信度兜底**：分类置信度低时，路由到人工客服而非通用 Agent
3. **多轮对话记忆**：不同轮次的问题可能属于不同意图，需要跨轮次的状态管理
