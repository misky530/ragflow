# Trip Planner — 产品经理视角

---

## 一、目标用户与核心痛点

| 用户类型 | 核心需求 | 当前痛点 |
|---|---|---|
| **自由行旅行者** | 制定个性化行程，不想依赖跟团 | 攻略分散在各平台，整合耗时 |
| **商务旅行者** | 快速规划出差行程，效率优先 | 需要同时考虑交通/住宿/会议时间 |
| **家庭出游** | 兼顾多人需求，行程要务实可执行 | 复杂变量多（孩子/老人偏好等） |
| **临时旅行** | 短时间内完成旅行决策 | 时间紧，不想做大量前期研究 |

**核心价值主张**：把"旅行规划"从"3~5 小时查攻略"压缩到"几分钟内得到可执行计划"——AI 自动整合行程、交通、住宿，用户只需描述需求。

## 二、功能设计的 PM 逻辑

### 2.1 三阶段专职分工 — 模拟旅行社内部流程

```
Tour Guide（行程策划）→ Transit & Stay（资源预订）→ Result Generator（旅行顾问）
```

这个三阶段设计映射了旅行社的真实分工：
- **Tour Guide**：像行程设计师，规划每天去哪、做什么
- **Transit & Stay**：像资源部，负责找交通和住宿方案
- **Result Generator**：像顾问，把所有信息整合成清晰报告

**PM 洞察**：每个 Agent 有明确边界，避免一个 Agent 既要规划又要搜索，导致质量下降。

### 2.2 双工具配置 — TavilySearch + TavilyExtract

Transit & Stay Agent 同时配备：
- **TavilySearch**：搜索交通/住宿选项（广）
- **TavilyExtract**：抓取特定页面详情（深）

**PM 洞察**：搜索（广）+ 抓取（深）的组合是信息获取的最优策略——先找到候选，再深入读取关键细节（价格、可用性、评分）。

### 2.3 对话模式 — 支持需求迭代

`mode: "conversational"` 意味着用户可以多轮对话：
- 第一轮：描述基本需求（去哪/几天/几人）
- 第二轮：追加偏好（不想坐夜车/需要亲子酒店）
- 第三轮：修改局部（把第三天行程换掉）

**PM 洞察**：旅行规划本质上是一个"需求迭代"过程，单轮问答无法满足，对话模式是必要设计。

## 三、产品边界

### 适用场景
- 国内/跨境休闲旅行规划
- 商务出差行程安排
- 节假日短途自由行

### 不适用场景

| 场景 | 原因 |
|---|---|
| **实时票务预订** | 模板只规划和搜索，不接入预订系统 |
| **签证/保险咨询** | 需要专业法律/保险知识，超出 AI 能力边界 |
| **极小众目的地** | TavilySearch 对小众地区信息覆盖不足 |
| **商业团体旅游** | 需要合同/发票等商务流程，AI 无法处理 |

## 四、产品成熟度评估

| 评估维度 | 评分 | 说明 |
|---|---|---|
| **需求真实性** | ★★★★★ | 旅行规划是高频、强需求场景 |
| **信息实时性** | ★★★☆☆ | 依赖 Tavily 联网搜索，但不能保证实时价格/可用性 |
| **计划可执行性** | ★★★☆☆ | 生成计划需要人工二次确认（特别是交通/住宿） |
| **个性化程度** | ★★★★☆ | 对话模式支持多轮需求细化 |

---

## 五、迭代方向

1. **接入真实预订 API**：直接调用机票/酒店 API，输出可预订的选项而非建议
2. **天气集成**：根据目的地天气调整户外/室内活动比例
3. **预算感知**：根据用户预算档次推荐不同价位方案
4. **行程导出**：输出为日历事件、PDF 或分享链接
