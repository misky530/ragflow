## 一、整体架构

### 节点类型全景

模板共使用 **6 种节点类型**：

| 节点类型 | 实例名 | 作用 |
|---|---|---|
| `Begin` | begin | 接收用户 query，启动流程 |
| `Agent`（主控） | NewPumasLick | Orchestrator，调度三个子 Agent |
| `Agent`（子） | FreeDucksObey | Web Search Specialist，URL 发现 |
| `Agent`（子） | WeakBoatsServe | Content Deep Reader，内容提取 |
| `Agent`（子） | SwiftToysTell | Research Synthesizer，分析合成 |
| `Tool` | FairToolsLive / SlickYearsCough | 外部工具节点，绑定 Tavily API |
| `Message` | OrangeYearsShake | 最终输出节点 |
| `Note` | 4个注释块 | Canvas 说明，不参与执行 |

**架构洞察**：RAGFlow 把 Tool 节点从 Agent 节点中解耦出来，单独作为图节点存在，理论上同一 Tool 节点可被多个 Agent 共享——当前模板未利用这一特性。

## 二、数据流

```
sys.query（用户输入）
        │
        ↓
Agent:NewPumasLick（Lead Agent）
  ├─ 调度 → Agent:FreeDucksObey
  │           └─ Tool:TavilySearch → 返回 URL 列表
  │           └─ 结果回流 Lead Agent
  │
  ├─ 调度 → Agent:WeakBoatsServe
  │           └─ Tool:TavilyExtract → 返回网页全文
  │           └─ 结果回流 Lead Agent
  │
  └─ 调度 → Agent:SwiftToysTell
              └─ 无工具，纯 LLM 合成
              └─ 结果回流 Lead Agent
                      │
                      ↓
            Message:OrangeYearsShake
            {Agent:NewPumasLick@content}
                      │
                      ↓
                  用户界面
```

**关键细节**：子 Agent 的输出**不直接传递给下一个子 Agent**，全部回流给 Lead Agent，由 Lead 决策后再调度下一阶段。Lead Agent 的 `message_history_window=12` 是整个流程的**信息中枢**，也是**上下文瓶颈**。

## 三、关键参数解析

### 模型选型梯度

| Agent | 模型 | 选型逻辑 |
|---|---|---|
| Lead Agent | qwen-max | 最强推理，负责决策调度 |
| Search Specialist | qwen-plus | 中等模型，工具调用任务不需要顶级推理，省成本 |
| Content Reader | moonshot-v1-auto | 网页长度不可预期，auto 自动适配 context window |
| Synthesizer | moonshot-v1-128k | 整合5-10个来源全文，128k 是硬性需求 |

### temperature 梯度

| Agent | temperature | 含义 |
|---|---|---|
| Lead Agent | 0.1 | 极低，确保调度逻辑稳定可预测 |
| 三个子 Agent | 0.2 | 略微放开，应对多样化网页内容的表达灵活性 |

### max_rounds 的含义

| Agent | max_rounds | 含义 |
|---|---|---|
| Lead Agent | 3 | 允许最多3轮对话（支持追问） |
| Search Specialist | 1 | 单次执行，防止无限搜索循环 |
| Content Reader | 3 | 允许重试，网页提取可能需多次尝试 |
| Synthesizer | 3 | 允许分段生成长报告 |

### frequency_penalty / presence_penalty（Lead Agent 独有）

Lead Agent 同时设置了 `frequency_penalty=0.5` 和 `presence_penalty=0.5`：
- `frequency_penalty`：降低重复 token 概率，防止调度指令中反复输出相同词汇
- `presence_penalty`：鼓励引入新话题，防止 Lead 在长上下文中注意力漂移

这说明设计者遇到过 Lead Agent **在多轮对话中自我重复**的问题，用这两个参数做了工程修正。

## 四、工具集成细节

### TavilySearch 配置

```json
{
  "days": 7,
  "max_results": 5,
  "search_depth": "basic",
  "topic": "general",
  "include_raw_content": true
}
```

| 参数 | 值 | 为什么这样设 |
|---|---|---|
| `search_depth` | basic | basic 比 advanced 便宜，且足够 URL 发现阶段使用 |
| `include_raw_content` | true | Search Agent 可做初步内容判断，减少不必要的 Extract 调用 |
| `days` | 7 | 保证时效性，但会过滤有价值的历史分析文章（trade-off） |
| `max_results` | 5 | 限制每次搜索返回量，控制下游提取成本 |

### TavilyExtract 配置

- 输出两个变量：`formalized_content`（结构化文本）和 `json`（原始数据数组）
- Content Reader 最多发起 **5-8 次**提取调用（system prompt 硬性限制）
- 这是整个流程**耗时最长的阶段**（3-5分钟）

## 五、已知架构局限

| 局限 | 技术原因 | 影响 |
|---|---|---|
| **子 Agent 串行执行** | RAGFlow Agent-to-Agent 为顺序调用 | 三阶段无法并行，总耗时是各阶段之和 |
| **Lead Agent 是单点瓶颈** | 所有中间结果经过 Lead 的 context | window=12 若撑不住长内容，信息会丢失 |
| **质量门控是 prompt 级别** | 靠 system prompt 描述标准，无代码强制 | LLM 可能"忘记"门控要求，无法保证100%执行 |
| **无并发保护** | 无 rate limiting 或 queue 机制 | 多用户同时使用可能触发 Tavily 限流 |
| **无中间状态持久化** | 每次运行无状态 | 运行中断后无法断点续跑，需从头开始 |

## 六、可扩展点

```
替换搜索工具
  TavilySearch → Bing Search API / Google Custom Search / SerpAPI
  修改 Tool 节点配置即可，无需改动 Agent 逻辑

替换模型
  Lead:       qwen-max      → claude-opus / gpt-4o
  Search:     qwen-plus     → gpt-4o-mini（成本相当）
  Reader:     moonshot-auto → claude-3-5-sonnet（200k context）
  Synthesizer: moonshot-128k → claude-3-5-sonnet / gpt-4o-128k

新增节点
  在 begin 后加 Categorize 节点
    → 路由简单查询（跳过 Stage 1-2）vs 复杂查询（完整流程）
  在 Synthesizer 前加 Retrieval 节点
    → 融合企业内部知识库，实现"公开信息 + 私有数据"混合研究

垂直化改造
  只需修改 Lead Agent system prompt，聚焦特定行业
  示例：金融研究版（只搜财经来源，输出含财务指标的分析）
  示例：法律研究版（只搜法规库，输出含法条引用的解读）
  改造成本：30分钟内可完成
```

## 七、落地配置

### 前置条件

| 资源 | 用途 | 获取渠道 |
|---|---|---|
| Tongyi-Qianwen API Key | Lead Agent + Search Agent | 阿里云百炼平台 |
| Moonshot API Key | Content Reader + Synthesizer | moonshot.cn |
| Tavily API Key | 搜索 + 提取 | tavily.com（免费1000次/月） |
| RAGFlow 实例 | 运行环境 | 自部署或 RAGFlow Cloud |

4个 API Key 缺一不可。

### 配置步骤

```
1. 设置 → 模型提供商 → 添加 Tongyi-Qianwen（填 API Key）
2. 设置 → 模型提供商 → 添加 Moonshot（填 API Key）
3. 设置 → 工具 → Tavily → 填 API Key
4. Agent → 新建 → 从模板创建 → 选择 Deep Research
5. 检查各 Agent 节点模型绑定是否正确
   （模板硬编码了模型 ID，账号中名称不一致时需手动修正）
6. 用 Straightforward 类型问题测试全链路
```

### 常见失败场景

| 症状 | 原因 | 排查与修复 |
|---|---|---|
| Stage 1 URL 数量不足 | 搜索词过于宽泛或小众 | 调整 Search Agent system prompt 的搜索策略 |
| Stage 2 大量提取失败 | 目标网页有反爬或需登录 | system prompt 增加"优先选择无需登录的来源" |
| 最终报告内容空洞 | Lead context 被中间内容撑满 | 降低 TavilyExtract 调用次数（8→5） |
| 整体耗时超 20 分钟 | Tavily 响应慢或 LLM API 排队 | 检查 Tavily 使用量；检查模型 API 响应时间 |
| 中文查询得英文报告 | Lead 语言自动检测失效 | system prompt 显式声明"以用户查询语言输出" |
| Lead 输出格式混乱 | 多轮对话上下文过长 | 减小 message_history_window 或降低子 Agent 输出详细度 |

### 运维监控建议

| 监控项 | 工具 | 告警阈值 |
|---|---|---|
| Tavily API 月度使用量 | Tavily 控制台 | 超过 800次/月 提前充值 |
| 单次查询耗时 | RAGFlow 执行日志 | 超过 20 分钟视为异常 |
| LLM API 错误率 | 各模型提供商控制台 | 连续 3 次失败人工介入 |
| 月度 API 总成本 | 各提供商账单 | 设置预算告警 |
