# Knowledge Base Report — 开发者视角

---

## 一、节点类型全景

| 节点类型 | 实例 | 作用 |
|---|---|---|
| `Begin` | begin | 接收用户研究问题 |
| `Agent` | 报告生成 Agent | 大规模检索 + 综合生成深度报告 |
| `Message` | 输出节点 | 展示报告 |

架构极简，但技术含量在**模型选型和 Retrieval 配置**上。

---

## 二、关键技术选型

### 模型：qwen3-235b

```
参数量：2350亿（235B）
上下文窗口：128K token
定位：顶级推理和长文本生成
```

选择 235b 而非普通模型的工程理由：
1. **长上下文处理**：综合报告需要同时处理数十个检索片段，普通 8K 模型直接截断
2. **多文档推理**：需要识别不同文档间的关联、时序关系、矛盾点，需要强推理能力
3. **长文本生成质量**：报告通常 1000~3000 词，大模型在长文本连贯性上显著优于小模型

### 128K Token 上下文的实际意义

```
1 个中文字符 ≈ 1.5~2 token
128K token ≈ 64,000~85,000 中文字符 ≈ 160~200 页 A4 文档

实际使用分配：
  System prompt：约 1K token
  检索到的文档片段（Top-K × 平均长度）：约 30~60K token
  用户问题：约 0.5K token
  生成报告（输出）：约 2~4K token
```

这意味着 Agent 可以同时"阅读"数十篇检索文档并综合生成报告。

## 三、Retrieval 配置建议

对于报告生成场景，Retrieval 参数需要与问答场景区别设置：

| 参数 | 问答场景推荐值 | 报告场景推荐值 | 原因 |
|---|---|---|---|
| `top_k` | 3~5 | 10~20 | 报告需要更广泛的知识覆盖 |
| `similarity_threshold` | 0.4~0.5 | 0.2~0.3 | 适当降低，避免遗漏相关内容 |
| `retrieval_mode` | 向量检索 | 混合检索 | 混合检索覆盖更全面 |
| `rerank` | 可选 | 推荐开启 | 大量片段时，重排序提升质量 |

## 四、System Prompt 设计要点

报告生成的 system prompt 应明确：

```
输出格式：
  - 执行摘要（200~300字）
  - 主体分析（分章节，每章 300~500字）
  - 关键发现（3~5条）
  - 结论与建议

质量要求：
  - 观点必须有文档支撑，不得凭空推断
  - 当文档信息不足时，明确说明"现有文档对此覆盖有限"
  - 当不同文档存在矛盾时，明确指出矛盾并给出判断依据

禁止行为：
  - 不得使用文档外的训练数据作为报告依据
  - 不得捏造数据或引用
```

## 五、成本估算

```
每次报告生成的 token 消耗：
  输入：系统提示(1K) + 检索内容(40K) + 问题(0.5K) ≈ 41.5K token
  输出：报告正文 ≈ 2~3K token

qwen3-235b 定价（参考）：
  输入：约 ¥4.5/M token → 每次报告输入约 ¥0.19
  输出：约 ¥18/M token → 每次报告输出约 ¥0.04~0.06
  合计：每次报告约 ¥0.23~0.25

与 technical_docs_qa 对比：
  后者每次约 ¥0.01~0.03（使用普通模型）
  报告生成成本约为问答的 10~20 倍
```

---

## 六、落地配置

```
1. 建立知识库（同 technical_docs_qa）
   注意：知识库内容质量直接决定报告质量
   建议每篇文档做好标题、摘要等 metadata

2. 导入模板，配置：
   - 模型：qwen3-235b（或其他支持长上下文的顶级模型）
   - Retrieval 参数：top_k=15, threshold=0.25, 混合检索

3. 配置 system prompt（报告格式和质量要求）

4. 测试：提一个需要综合多个文档才能回答的研究问题
   观察报告的结构、引用准确性和内容完整性
```
