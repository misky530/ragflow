# Knowledge Base Report — 产品经理视角

---

## 一、目标用户与核心痛点

| 用户类型 | 核心需求 | 当前痛点 |
|---|---|---|
| 企业研究员/分析师 | 基于内部文档生成完整研究报告 | 人工阅读大量文档后才能综合写报告，耗时数小时 |
| 管理层 | 快速获取某一主题的内部知识综述 | 散落在各处的文档无法快速汇总 |
| 咨询/法务团队 | 从知识库中提取某议题的所有相关内容 | 搜索只能找到单个文档，无法自动综合 |
| 新员工培训 | 快速了解某一业务领域的全貌 | 需要阅读大量文档才能建立整体认知 |

**核心价值主张**：不是"找答案"，而是"生成报告"——把知识库里关于某个主题的所有相关内容，自动综合成一份有结构的深度报告。

---

## 二、功能设计的 PM 逻辑

### 2.1 从"问答"到"报告"的产品升级

`technical_docs_qa` 解决的是**单一问题的精准检索**；`knowledge_base_report` 解决的是**复杂主题的全面综合**：

| 对比维度 | technical_docs_qa | knowledge_base_report |
|---|---|---|
| 用户意图 | 找到一个具体答案 | 生成一份综合报告 |
| 检索范围 | 最相关的 3~5 个片段 | 可能涵盖数十个相关文档 |
| 输出形式 | 简洁回答 | 结构化报告（摘要+分析+结论） |
| 适合问题类型 | "X 功能的 API 是什么？" | "分析我们过去两年的技术演进历程" |

### 2.2 超大模型的产品意义

使用 qwen3-235b（千亿参数）+ 128K token 上下文，是为了承载**大规模知识综合**的需求：
- 可以同时"看到"数十个检索到的文档片段
- 更强的推理能力，识别文档间的关联、矛盾和规律
- 更优质的长文本生成能力（报告通常需要 1000+ 词）

## 三、产品边界

### 适用场景
- 企业内部研究报告生成（年度总结、技术白皮书）
- 基于历史文档的现状分析
- 多文档综合的尽职调查辅助
- 新员工入职培训材料自动生成

### 不适用场景

| 场景 | 原因 | 替代方案 |
|---|---|---|
| 简单问答 | 用大模型成本高，technical_docs_qa 够用 | `technical_docs_qa` |
| 需要联网信息 | 仅检索内部知识库 | `web_search_assistant` |
| 实时数据分析 | 知识库是静态文档 | `sql_assistant` |

## 四、产品成熟度评估

| 评估维度 | 评分 | 说明 |
|---|---|---|
| **需求真实性** | ★★★★★ | 企业内部报告生成是高频高价值需求 |
| **技术合理性** | ★★★★★ | 大模型 + 长上下文是该场景的正确选型 |
| **成本** | ★★☆☆☆ | qwen3-235b 是高成本模型，报告生成每次费用较高 |
| **知识库依赖** | ★★★☆☆ | 报告质量完全取决于知识库的内容质量和覆盖度 |

---

## 五、迭代方向建议

1. **报告模板定制**：支持用户选择报告结构（技术报告/商业分析/合规审查等不同格式）
2. **引用溯源**：报告中每个观点标注来自哪份文档的哪个章节
3. **报告导出**：支持导出为 PDF/Word，方便直接使用
4. **成本分级**：简单综合用小模型，复杂报告用大模型，降低平均成本
