# CV Analysis — 开发者视角

> 关注：节点怎么设计的？数据怎么流转？有哪些坑？怎么改造和落地？

---

## 一、节点类型全景

模板仅用 **5 种节点类型**，是 RAGFlow 模板库中结构最精简的：

| 节点类型 | 实例名 | 作用 |
|---|---|---|
| `Begin` | begin | 对话入口，接收 JD 文字输入 |
| `Iteration` | PetiteBanksWarn | 遍历 `sys.files`，驱动批量处理 |
| `IterationItem` | EagerGiftsOpen | Iteration 内部起始节点，输出当前文件和索引 |
| `Agent` | AfraidBearsShare | 核心处理：简历解析 + JD 匹配评分 |
| `Message` | TenLizardsShake | 输出评估结果到聊天界面 |

无 Tool 节点，无外部 API 调用，整个流程完全在 RAGFlow + LLM 内部闭环。

## 二、数据流分析

```
begin 节点
  ├── begin@JD           ← 用户手动粘贴的职位描述文字
  └── sys.files          ← 用户上传的简历文件列表
          │
          ↓
Iteration:PetiteBanksWarn（遍历 sys.files）
          │
          ↓ 每次迭代
IterationItem:EagerGiftsOpen
  ├── @index             ← 当前简历序号（从 0 开始）
  └── @item              ← 当前简历文件内容
          │
          ↓
Agent:AfraidBearsShare
  user prompt 拼接：
  ┌──────────────────────────────────────────┐
  │ HR is asking about: {sys.query}          │ ← 用户追问（可选）
  │ Job description is {begin@JD}            │ ← 来自 begin 节点
  │ Resume is {IterationItem:EagerGiftsOpen@item} │ ← 当前简历
  └──────────────────────────────────────────┘
          │ 输出 @content
          ↓
Message:TenLizardsShake
  内容：{Agent:AfraidBearsShare@content}
          │
          ↓ 逐份实时输出（不等全部完成）
      聊天界面

Iteration 容器聚合输出：
  evaluation: Array<string>  ← 所有简历评估的结果数组（当前无下游消费）
```

## 三、三个已知设计问题

### 问题 1：`@index` 从未被使用

`IterationItem@index` 暴露了当前简历的序号，但 Agent 的 user prompt 和 system prompt 都没有引用它。

**后果**：批量输出时无法自动标注"第1位候选人/第2位候选人"，HR 无法对应到具体文件。

**修复成本极低**，在 user prompt 首行加一行即可：
```
This is candidate #{IterationItem:EagerGiftsOpen@index + 1}
```

---

### 问题 2：`message_history_window=12` 跨简历污染

Iteration 每次调用的是**同一个 Agent 实例**。window=12 意味着处理第5份简历时，Agent 上下文里可能还残留第1-4份简历的内容。

**后果**：
- 评分受前序简历影响（对比效应，非独立评估）
- 上下文过长后早期内容被截断，影响一致性

**修复**：将 `message_history_window` 从 12 降至 1，或在 system prompt 首行加：
```
Evaluate ONLY the current resume below. Ignore all previous context.
```

---

### 问题 3：Iteration 聚合结果无人消费

Iteration 容器将所有 `Agent@content` 聚合为 `evaluation: Array<string>`，但当前没有任何后续节点引用它。

**含义**：这是预留的扩展接口，团队已预见到需要汇总排序的需求，但尚未实现。接入汇总 Agent 是最直接的下一步改造。

## 四、关键参数解析

### Begin 节点的输入设计

```json
{
  "type": "line",
  "name": "Job Description",
  "required": true
}
```

JD 以**文本输入**而非文件上传。简历通过 `sys.files` 处理——两种输入方式不一致，存在 UX 摩擦（用户需手动粘贴 JD）。

### Agent 参数

| 参数 | 值 | 工程含义 |
|---|---|---|
| `temperature` | 0.1 | 极低随机性，确保100份简历评分标准一致 |
| `max_rounds` | 1 | 每份简历单次处理，不允许追问重试 |
| `max_retries` | 1 | 失败不重试，直接跳过该简历（用户无感知） |
| `message_history_window` | 12 | 跨迭代保留上下文（见问题2） |

### Iteration 的 items_ref

```json
"items_ref": "sys.files"
```

直接引用系统全局文件列表，**无法过滤文件类型**——用户误传非简历文件（图片、合同）时，系统也会尝试处理。

## 五、system prompt 质量问题

### 编号跳跃（小问题，说明模板有修改历史）

```
### 1. Standardized Information Extraction
### 3. JD Matching Analysis     ← 直接跳到第3条，第2条缺失
```

### 字符数限制过于极端

```
Content length must always be between 30-50 characters
```

30-50个字符（约半句话）对匹配分析来说极短，可能导致 LLM 截断有价值的分析，或为凑字数填充无意义内容。建议改为 50-100字。

### 输出规范自相矛盾

同时要求"No subheadings"和输出6个字段，纯文本无结构的情况下 HR 需自己辨别哪行是姓名、哪行是评分。建议改用简单分隔符（如 `---`）而非完全禁用结构。

## 六、已知架构局限

| 局限 | 技术原因 | 影响 |
|---|---|---|
| 无文件类型校验 | Iteration 盲目遍历 sys.files | 非简历文件触发无效处理 |
| 评估非独立 | window 跨迭代保留上下文 | 评分受前序简历影响 |
| 无序号标注 | @index 未被 Agent 使用 | 输出无法对应到文件名 |
| 无汇总排序 | 聚合结果无后续消费节点 | 批量处理后无法自动输出 Top N |
| 失败无感知 | max_retries=1，失败即跳过 | 某份简历解析失败用户不知道 |
| 结果不持久化 | Message 节点仅输出到聊天 | 刷新页面后结果丢失 |

## 七、可扩展点

```
修复序号问题（5分钟）
  user prompt 首行加：
  "This is candidate #{IterationItem:EagerGiftsOpen@index + 1}"

添加汇总排序节点（1-2小时）
  在 Iteration 容器后新增 Agent 节点
  输入：{Iteration:PetiteBanksWarn@evaluation}
  system prompt：按 Score 排序，输出 Top 3 推荐 + Markdown 表格

增加人工审核分流（2-3小时）
  在 Agent 后加 Categorize 节点
  条件路由：Score≥7 → 推荐 / Score 4-6 → 人工复核 / Score<4 → 过滤

接入 Google Sheets MCP（半天）
  在 Message 节点并行新增 MCP Tool 节点
  将 Agent@content 写入预设 Google Sheet

替换为本地模型（企业合规，半天）
  DeepSeek Chat → Ollama 部署的 Qwen2.5 / DeepSeek-R1-7B
  数据完全不出域，成本趋近于零

垂直化改造：技术岗（5分钟）
  在 system prompt 字段列表追加：
  - Tech Stack: 技术栈（编程语言、框架、工具）
  - GitHub/Portfolio: 如有则提取链接
  - Project Highlight: 最相关项目经历（一句话）
```

## 八、落地配置

### 前置条件

| 资源 | 用途 | 预计月成本 |
|---|---|---|
| DeepSeek API Key | 简历解析和评分 | 处理1000份简历约 ¥5-15 |
| RAGFlow 实例 | 运行环境 | — |

1个 API Key，所有模板中门槛最低。

### 配置步骤

```
1. 设置 → 模型提供商 → 添加 DeepSeek → 填入 API Key
2. Agent → 新建 → 从模板创建 → 选择 CV Analysis
3. 测试单份简历（文字型 PDF + JD 文字）
   验证：6个字段是否正确提取，评分是否合理
4. 测试批量（5份不同格式）
   验证：结果是否清晰分隔，有无跨简历内容混淆
5. 根据岗位特性调整 system prompt（可选）
```

### 简历格式实际表现

| 简历格式 | 解析质量 | 注意事项 |
|---|---|---|
| 文字型 PDF | ★★★★★ | 最佳，直接提取无损 |
| Word (.docx) | ★★★★☆ | 格式信息丢失但内容完整 |
| 图片型 PDF / 扫描件 | ★★☆☆☆ | 依赖 OCR，中英文混排效果差 |
| 多栏设计型简历 | ★★★☆☆ | 文字提取顺序可能错乱 |
| 含大量表格的简历 | ★★★☆☆ | 内容可提取，结构信息丢失 |

**落地建议**：在用户引导中明确要求"上传文字型 PDF 或 Word 格式"，主动规避 OCR 场景。

### 常见失败场景

| 症状 | 原因 | 修复 |
|---|---|---|
| 某字段显示"未找到" | 简历缺该信息或格式导致漏提取 | system prompt 加"若无法提取则输出 N/A" |
| 多份简历内容混淆 | window 保留了前序简历内容 | 将 window 从 12 降至 1 |
| 所有简历评分相近 | 对比效应 / LLM 对评分尺度理解不一致 | system prompt 加具体评分示例（8分=满足所有硬性要求） |
| 输出语言变为英文 | 英文简历触发了语言跟随 | system prompt 强化"无论简历语言，输出必须为中文" |
| 批量中途停止 | DeepSeek API 超时或限速 | 减小批次（建议单次不超过20份） |
| 图片简历输出空内容 | 文本提取失败，传入空字符串 | 增加文档预处理节点，或在引导中说明格式要求 |

### 批量处理规模建议

| 批次大小 | 预计耗时 | 建议 |
|---|---|---|
| 1-10 份 | 1-3 分钟 | 实时等待 |
| 10-30 份 | 3-10 分钟 | 可后台运行 |
| 30-100 份 | 10-35 分钟 | 建议分批提交 |
| 100+ 份 | 35分钟以上 | 拆分为多个30份批次 |
