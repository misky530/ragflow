# Customer Support — 开发者视角

---

## 一、与 customer_service 的架构差异

```
customer_service 的分支汇合方式：
  分支A Agent → ┐
  分支B Agent → ├─ VariableAggregator → Message
  分支C Agent → ┘

customer_support 的分支汇合方式：
  分支A Agent → ┐
  分支B Agent → ├─ Message（框架内部处理非执行分支）
  分支C Agent → ┘
```

**关键问题**：多个分支都连接到同一个 Message 节点，但每次只有一个分支执行，RAGFlow 如何保证 Message 只显示实际执行分支的内容？

这依赖 RAGFlow 的**条件激活机制**：
- 执行引擎追踪哪个分支被激活
- 未激活分支的输出变量为 null / 空
- Message 节点在渲染时跳过空变量，只展示有值的输出

---

## 二、两种方案的工程对比

| 维度 | VariableAggregator（customer_service） | 直连 Message（customer_support） |
|---|---|---|
| 数据流透明度 | 高（汇合点可见） | 低（依赖框架内部） |
| 调试难度 | 低（可查看 Aggregator 的输入） | 高（需要理解框架条件激活） |
| 节点数量 | 多一个 VariableAggregator | 更少 |
| 出错风险 | 低（显式配置） | 中（依赖隐式行为） |

**开发建议**：如果团队对 RAGFlow 不熟悉，优先选择 `customer_service` 的 VariableAggregator 方式，行为更可预测。
