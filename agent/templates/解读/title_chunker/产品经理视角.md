# Title Chunker — 产品经理视角

---

## 一、解决什么问题？

标准的 Splitter（按字数/token 数切分）有一个根本性问题：**切片可能在章节中间截断**，导致：
- 一个切片包含了两个章节的内容（语义混乱）
- 重要的章节标题和对应内容被分到不同切片（语义断裂）

Title Chunker 的解法：**按文档标题层级切分**，每个切片 = 一个完整的章节单元（标题+对应正文）。

```
传统切分（按 token）：
  切片1: "...第一章结尾内容\n## 第二章开始..."  ← 语义混乱
  切片2: "...第二章内容\n## 第三章开始..."

标题切分：
  切片1: "## 第一章\n第一章全部内容"           ← 语义完整
  切片2: "## 第二章\n第二章全部内容"
```

**核心价值主张**：让每个索引单元等于一个语义完整的章节——检索时直接命中相关章节，无需担心切割噪声。

## 二、功能设计的 PM 逻辑

### 2.1 HierarchicalMerger — 结构感知的核心组件

这是 Title Chunker 区别于其他摄取模板的唯一关键组件：

```
hierarchy=3（合并到第 3 层深度）
Level 0：H1 "# "
Level 1：H2 "## "
Level 2：H3 "### "
Level 3：H4 "#### "
```

**PM 洞察**：`hierarchy=3` 的含义是"把 H4 级别的小节内容合并到其上级章节"。这保证了切片有足够的语义完整性，不会因为过细的标题层级产生太碎的切片。

### 2.2 无 LLM 调用 — 成本最低的增强方案

Title Chunker 是三个 Ingestion Pipeline 模板中**唯一不调用 LLM** 的：
- 纯规则切分，基于正则表达式匹配标题
- 摄取成本 ≈ 基础摄取（无额外 API 调用）
- 摄取速度最快

**PM 洞察**：对于有标题结构的文档，利用文档自身结构信息比 LLM 生成摘要更可靠——因为文档作者的标题就是最好的"摘要"。

## 三、产品边界

### 适用场景

| 文档类型 | 为什么适合 |
|---|---|
| 产品手册 | 章节结构清晰（安装/配置/故障排除）|
| 法律合同 | 条款编号就是标题层级 |
| 技术文档/API 文档 | Markdown 格式天然带有 H1~H4 |
| 学术论文 | 摘要/引言/方法/结论 结构明确 |
| 研究报告 | 各章节独立可检索 |

### 不适用场景

| 场景 | 原因 |
|---|---|
| **无标题的文章** | HierarchicalMerger 无法找到切分点，退化为单块 |
| **标题不规范的文档** | 标题格式不符合 Markdown 规范，正则匹配失效 |
| **需要 LLM 增强检索** | 本模板不生成摘要/关键词，检索维度单一 |

## 四、产品成熟度评估

| 评估维度 | 评分 | 说明 |
|---|---|---|
| **切片语义完整性** | ★★★★★ | 按章节切分，语义完整 |
| **摄取成本** | ★★★★★ | 无 LLM 调用，成本最低 |
| **摄取速度** | ★★★★★ | 纯规则，处理最快 |
| **适用文档类型** | ★★★☆☆ | 仅适合有标题结构的文档 |
| **检索精度** | ★★★☆☆ | 切片完整但无摘要增强，检索依赖原文质量 |

## 五、迭代方向

1. **自动标题检测**：对无 Markdown 标题的文档，用 LLM 自动识别标题边界
2. **与 Extractor 结合**：在 HierarchicalMerger 后增加 Extractor 生成摘要，实现结构+语义双重增强
3. **标题前缀继承**：切片中保留父级标题作为上下文（"Chapter 1 > Section 2.1"）
