# Chunk Summary — 开发者视角

---

## 一、架构概览

```
File
  ↓
Parser:HipSignsRhyme（多格式解析，pdf→json, word→json, text→text）
  ↓
Splitter:LateExpertsFeel（512 tokens，"\n"分割，overlap=0）
  ↓
Extractor:YummyGhostsType（field_name="summary"，deepseek-chat）
  ↓
Tokenizer:EightRocketsAppear（fields="summary"，embedding+full_text）
```

**canvas_category**: `"dataflow_canvas"`

---

## 二、核心技术细节

### 关键设计：Tokenizer `fields="summary"`

```json
// Tokenizer 配置
{
  "fields": "summary",         // ← 关键：索引摘要字段，不是原文
  "search_method": ["embedding", "full_text"],
  "filename_embd_weight": 0.1
}
```

对比 advanced_ingestion_pipeline：
```json
{
  "fields": "text",            // 索引原文
  ...
}
```

**机制**：当 `fields="summary"` 时，RAGFlow 在建立向量索引和全文索引时使用 `summary` 字段内容，但召回时返回的 chunk 对象包含完整的 `text` 字段（原文）。

### Extractor 配置

```json
{
  "component_name": "Extractor",
  "params": {
    "field_name": "summary",
    "llm_id": "deepseek-chat@DeepSeek",
    "max_tokens": 256,
    "temperature": 0.1,
    "sys_prompt": "Act as a precise summarizer..."
  }
}
```

- `field_name`: 生成的摘要存储在 chunk 的 `summary` 字段
- 输出的 chunks 数组：每个 chunk 新增 `summary` 属性

---

## 三、与 advanced_ingestion_pipeline 对比

| 维度 | chunk_summary | advanced_ingestion_pipeline |
|---|---|---|
| Extractor 数量 | 1（summary） | 4（summary/keywords/questions/metadata）|
| Tokenizer fields | "summary" | "text" |
| 摄取时间 | ~1× 基础 | ~4× 基础 |
| 召回维度 | 语义（摘要） | 语义+关键词+问答+元数据 |
| 适合场景 | 噪声文档，需要精准语义 | 需要多维检索 |

## 四、数据结构

摄取后每个 chunk 的字段：

```json
{
  "text": "原始文本内容（完整，含格式噪声）",
  "summary": "LLM 生成的精炼摘要",
  "vector": [0.1, 0.2, ...],  // 基于 summary 生成的向量
  "tokens": "基于 summary 的全文索引词"
}
```

检索命中时返回的是完整 chunk 对象（包含 `text` 原文）。

---

## 五、Splitter vs Parser 输出格式

```json
// chunk_summary 中 Parser 配置
{
  "pdf": {"output_format": "json"},   // ← json（保留结构）
  "word": {"output_format": "json"},
  "text&markdown": {"output_format": "text"}
}
```

注意：这里 PDF 输出 json（保留块结构），而 advanced_ingestion_pipeline 的 PDF 输出 markdown。两种格式对 Splitter 行为可能有细微差异。

## 六、部署要点

```
1. 配置 DeepSeek API Key（单 Extractor）
2. Extractor max_tokens=256——摘要长度被限制，非常长的切片摘要可能不完整
3. Splitter overlap=0——切片不重叠，适合摘要后语义完整的场景
4. 如果发现召回结果缺少关键细节，考虑切换到 advanced_ingestion_pipeline
5. 调试技巧：查看 chunk 对象的 summary 字段，确认摘要质量
```
